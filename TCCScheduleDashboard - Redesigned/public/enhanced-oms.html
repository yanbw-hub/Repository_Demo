Enhanced OMS

Internal tool for validating, previewing and batch-updating OM Period values in the SQL-backed OMS table. It is designed for safe updates based on uploaded order rows, duplicate detection and controlled write-back to the target database table.

  • Preview valid, duplicate and invalid records before update

  • Check database connection health before major changes

Guide Manual

This guide explains how to use the Enhanced OMS app to safely update OM Period values in the target SQL table. The system is structured around a simple workflow: check connection, prepare input rows, preview the matched records, then commit the update.

  1. Health Check

    Before uploading or updating anything, use the system health indicator to confirm that the backend can connect to the configured SQL source.

    • A healthy status means the backend, ODC metadata and SQL connection are all available.
    • If the status is unavailable, do not continue with bulk changes until the connection issue is resolved.
    • Use this step before every important update batch.
  2. Prepare Input Rows

    The app expects rows that identify orders by SalesDoc and Item. These values are normalized before matching against the target SQL records.

    • Keep SalesDoc and Item clean and consistent with the database format.
    • Remove accidental blank rows before submitting the batch.
    • If your source contains repeated rows, the app will separate duplicates during preview.
  3. Preview Before Update

    The preview step validates the submitted rows and summarizes how many are unique, duplicated or invalid.

    • Review the valid row count before committing any update.
    • Check invalid rows carefully to catch formatting mistakes.
    • Use preview as the main safety layer before writing to SQL.
  4. Choose OM Period

    After previewing the rows, select the target OM Period that should be written back to the matching records.

    • Make sure the chosen period is the correct business period for the affected orders.
    • One batch should only apply one OM Period value at a time.
    • If you need to apply different OM Period values, split the data into separate batches.
  5. Run Bulk Update

    When the preview results look correct, submit the update to write the OM Period value into the target SQL table.

    • The system updates matched records in chunks to reduce risk and improve stability.
    • Only validated record IDs are included in the write-back.
    • Review the returned affected-row count after each run.
  6. Error Handling

    All important failures are returned as JSON errors from the backend so you can inspect them quickly in the browser network panel or terminal logs.

    • Connection issues usually appear during the health-check step.
    • Validation issues usually appear during preview.
    • Update issues usually appear as 4xx or 5xx responses with a backend error message.
  7. Recommended Working Practice

    Use small test batches first, confirm the result in SQL, then proceed with the full batch.

    • Start with a few known orders when deploying or testing.
    • Keep a copy of the input rows used for each update batch.
    • Coordinate with planning or scheduling owners before changing large volumes.

General Suggestion: always follow the sequence Health Check → Preview → Validate → Bulk Update. This keeps the process transparent and reduces the chance of writing incorrect OM Period values into the production table.

1. Connection & system metadata

GET /api/health
Check whether the backend is alive and whether it can connect to the configured SQL source. Also returns a brief connection summary, including target database, schema and table.

2. Input validation & preview

POST /api/preview
Validate incoming rows before update. The payload is typically { rows: [...] }. The response includes: inputRowCount, validUniqueInputCount, duplicateInputCount, invalidRowCount, validRows and invalidRows.

3. Bulk OM Period update

POST /api/update-omperiod
Commit the selected OM Period to the validated rows in the target SQL table. Typical payload: { rows: [...], omPeriod: "P4" }.
Update behavior
The backend resolves target IDs first, then updates the OM Period column in chunks to improve reliability for larger batches.

4. Core matching logic

Matching keys
Records are identified using the configured SalesDoc and Item columns, while the update is ultimately applied to the resolved SQL row IDs.
Configured columns
The backend reads its target column names from environment variables such as OM_DB_ID_COLUMN, OM_DB_SALESDOC_COLUMN, OM_DB_ITEM_COLUMN and OM_DB_OMPERIOD_COLUMN.
Configured target table
The destination SQL table is derived from the ODC / env configuration and is normally the OMS comments / OM Period table used by scheduling.

5. Expected JSON responses

Success
Successful requests return JSON with ok: true plus additional payload details.
Failure
Failed requests return HTTP 4xx or 5xx responses with ok: false and an error message.

6. Operational notes

Use this tool only on the internal network. For high-volume changes, validate a small batch first and confirm the output in SQL before applying the full update set.
